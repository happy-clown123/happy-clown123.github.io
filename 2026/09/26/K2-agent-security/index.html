Agent 安全专题（K 模块深入）

Agent 安全专题（Agent Security Engineering）

定位：作为模块 K 的深入子篇，把 prompt injection 扩展到“有工具、有记忆、能改变外部状态”的 Agent 系统。
前置：模块 F（LLM 基础）、G/H（网络与 Web 信任边界）、K §2.1（prompt injection）｜后继：模块 M（红队评测）、O（论文复现）。
及格线：能为一个带 tool/RAG/memory 的 Agent 画出数据流与信任边界，用确定性策略拦住越权动作，并同时报告 USR/ASR/UAR/FPR。

1 威胁模型：不要从 payload 清单开始

1.1 系统分解

Agent 不是“一个更会思考的 LLM”，而是一个分布式软件系统：

先列五类东西：

  • 资产：用户数据、token、文件、交易权限、业务状态、审计日志。
  • 主体：用户、Agent 运行时、MCP client/server、工具服务账号、其他 Agent。
  • 入口：user prompt、网页/邮件、RAG 文档、tool result、memory、工具元数据。
  • 危险出口：外发消息、资金转移、写文件、执行代码、改权限、写长期记忆。
  • 信任边界：穿过边界的内容必须被身份验证、授权、校验或降权。

1.2 两个必要条件

把一次危险事件简化为：

提示过滤主要降低前一项，最小权限、scope、确认和沙箱主要压低后一项。只改 prompt，却给 Agent 整个邮箱、文件系统和 shell 权限，不是系统级防御。

先产出威胁模型：阅读 OWASP Agentic Threats and Mitigations 后，复制 projects/secure-agent/threat-model.md 的结构，为你自己的目标系统画数据流。至少标出 5 条信任边界、3 个危险出口和每个出口的授权组件；没完成这张图前不要开始收集 payload。

2 Agent hijacking：指令和数据共用语言通道

是什么：攻击者把指令藏在 Agent 必须读取的邮件、网页、代码仓库或文档中，让 Agent 把外部数据误当成新任务。

关键区分：

概念 攻击者控制什么 直接危害
Jailbreak 用户直接 prompt 诱导模型输出违背行为策略的内容
Direct prompt injection 用户输入中的伪指令 篡改应用任务或泄露上下文
Indirect prompt injection / hijacking Agent 遇到的外部数据 借已授权工具读数据、外发或改状态

NIST 用 AgentDojo 做的测试强调：评测不能只问“模型有没有说出危险文本”，应该检查攻击目标动作是否真的发生。

阅读任务：先读 Greshake 2023 间接注入笔记，再读 AgentDojo 笔记。分别写出 attacker control、benign task、attack goal、observable external state 四项；读完后才能设计 K07 的新增场景。

3 工具安全：模型只有建议权

安全调用链应该是：

3.1 授权要看参数

读图时追踪两条输入：网页/记忆进入 planner，已认证身份与受控策略进入 gateway。即使文档写着“管理员已批准”，它也不能跨到第二条输入里。认证回答“是谁”，授权回答“能对哪个资源做什么”，执行回执回答“是否真的发生”；三者应分别留下证据。

贯穿示例：用户要求“总结内部文档”，检索内容却要求把全文发送给外部地址。模型提案 send_email 说明规划可能被影响；网关拒绝说明动作被拦住；只有邮件系统回执才能证明实际外发。不要把危险文本、危险提案、放行事件全算成同一种 ASR。

“允许调用 send_email”不等于“允许给任意收件人发任意内容”。一次授权决策至少要包含：

实验 k04 用白名单、schema、资源 scope 和人工确认实现最小网关。关键是 fail closed：遇到未知工具、多余参数或缺失上下文时拒绝，而不是“尽量猜”。

学到这里立刻做｜K04：运行 labs/k04_agent_tool_boundary.py，为每个拒绝 case 标注它属于 allowlist、schema、resource scope 还是 confirmation。再新增一个“合法工具名 + 非字典 args”case，并在仓库根目录运行 python -m unittest discover -s tests -p "test_security_controls.py" -v。产物是一张 allow/deny 决策表，不是终端截图。

3.2 Human-in-the-loop 不是一个确认按钮

有效确认必须在执行前展示完整的工具、目标资源、关键参数和后果，且确认不能被模型代替。对每次无害读操作都弹窗会造成确认疲劳，应按动作风险分级。

确认还要绑定本次动作：主体、规范化参数、最终资源、内容摘要和有效期。若路由别名仍叫 team，实际收件人已经变了，旧确认不能自动沿用。执行器应在提交边界重新验证相关状态，并按真实工具能力采用原子操作、版本前置条件或重新确认；“检查后再执行”之间仍可能有 TOCTOU 窗口。

K04 的 user_confirmed: bool 只是教学输入，不是防重放授权凭证；它没有实现参数绑定、过期或原子提交。学习时先指出这些边界，不把玩具网关当完整生产实现。参见 Mind the Gap（2025） 与 Commit-Time Authorization（2026）。

4 Memory 安全：跨会话的持久攻击面

延伸动手：读完上图与 §3.2 后，把 K04 的一个外发场景写成三行记录：proposal / authorization / execution_result。K04/K07 没有真实执行器，因此最后一栏填“未执行，固定夹具”，不要填“真实邮件发送失败”。再打开项目 pipeline.py，确认它返回的是决策事件。

Memory 投毒比单轮注入更难查：恶意内容可在会话 A 写入，到会话 B 才影响规划。每条记忆至少带：

三条原则：

  1. 写入时验证不能替代读取时授权；主体和任务可能已变。
  2. 外部检索内容不应自动升格为高信任长期记忆。
  3. 要支持删除、过期、溯源和租户隔离，并对异常写入频率告警。

学到这里立刻做｜K05：运行 labs/k05_memory_poisoning.py，逐条解释 wrong tenant、expired、untrusted source。再增加 allowed_uses 思考题：一条可用于“个性化回答”的记忆，为什么不能自动用于“授权转账”？可对照项目里的 memory_store.py。

5 MCP 安全：协议不会自动带来信任

MCP 标准化了 client 如何发现和调用工具，但工具描述、server 响应和返回数据仍是不可信输入。学 MCP 安全时优先掌握：

  • server 身份和来源：安装前审查、固定版本/hash、最小运行权限。
  • OAuth 边界：验证 issuer/audience/scope，不把上游 token 原样透传给下游。
  • per-tool authorization：公开读工具和敏感写工具不共用一个过宽 scope。
  • confused deputy：server 必须确认“谁”在代理“谁”对“什么资源”做什么。
  • 工具变更：工具名、描述、schema 或权限变更时重新审批，防止 rug pull。

请始终对照当前 MCP 规范；协议更新快，不要背某个历史版本字段。

5.1 Tool manifest rug pull

客户端第一次安装时看到的工具描述、参数 schema 和权限，可能在后续发现阶段被同名工具静默替换。危险不只来自描述里出现明显恶意句子，因此“扫描 ignore previous instructions”不是供应链控制。

更可靠的最小流程是：

  1. 固定并验证 MCP server 身份和发布来源。
  2. 对 server identity + tool name + version + description + schema + permissions 生成规范化指纹。
  3. 每次发现和调用前与审批记录比对；任何变化 fail closed。
  4. 权限扩大必须单独拒绝，不能因为名称和版本号没变就放行。
  5. 新指纹只有在人工/发布流程重新审查代码、权限和运行沙箱后才能登记。

K08 用 SHA-256 指纹离线演示这一流程。指纹只能回答“是否变化”，不能证明初始版本安全，也不能替代签名、制品来源证明和运行时沙箱。

学到这里立刻做｜K08：先浏览 MCP 当前规范 的 authorization 与 security 相关页面，再运行 labs/k08_mcp_manifest_rug_pull.py。接着阅读 Parasites in the Toolchain 笔记，回答“指纹、发布者身份、代码审计、运行沙箱”分别解决哪一层风险。

6 评测：安全和可用性必须一起量

6.1 四个最小指标

好的防御希望 USR 高，ASR/UAR/FPR 低。只报“攻击阻断率 100%”没有意义：把所有工具禁用也能得到这个数，但 Agent 已经不能完成任务。

先检查分母：没有攻击场景时 ASR 是“未测”，不是 0%；没有放行动作时 UAR 无定义。K06 用 NaN 表示这种情况，报告请写 N/A (0/0)。还要区分无攻击任务效用与攻击条件下任务效用；本例 USR 只统计前者。UAR 是本仓约定，引用论文时先核对它的分母是否相同。

6.2 评测集设计

  • 每个攻击场景要有配对的 benign task，保证防御没有破坏效用。
  • 同时标注文本输出、工具提案、网关决策和最终外部状态。
  • 多次采样；生成模型不是确定性程序，一次没成功不等于安全。
  • 保存失败 case 而不是只保存平均分，便于建立回归测试。

学到这里立刻做｜K06：运行 labs/k06_agent_security_eval.py，不用代码手算四个指标；然后构造“全部工具都禁用”的场景，验证 ASR 可以为 0 但 USR/FPR 很差。把分子、分母和失败 case 一起写进报告。

集成验收｜K07 + 项目：先运行 labs/k07_secure_agent_pipeline.py，沿一条攻击 case 追踪 observation → proposal → gateway → audit → metric；再按 projects/secure-agent/README.md 运行作品集 demo，检查日志正文已脱敏。最后执行仓库根目录的 python tools/check_labs.py，保留测试汇总和一条脱敏审计事件作为证据。

评审时最有价值的不是“用了哪个 Agent 框架”，而是你能否解释一个攻击如何穿过信任边界、哪个确定性控制把它拦住、这个控制产生了多少误拦。

8 常见误区

  1. 把 system prompt 当权限系统：它是模型输入，不是可强制执行的 access control。
  2. 过滤“ignore previous instructions”就算防注入：攻击可用任意语言和间接表述；防御重点应是危险动作边界。
  3. 工具 allowlist 等于安全：合法工具仍可以携带恶意参数，必须做资源和参数级授权。
  4. 长期记忆是“模型自己记得的”，所以可信：memory 是数据库，有传播、跨租户、过期和投毒问题。
  5. 只跑一次攻击：模型采样有随机性；应该做多次、自适应、任务分组评测。
  6. 为了安全禁用所有工具：这只是把效用归零；要同时报告 USR 和 FPR。

11 检查点

  • 画出一个 tool-using Agent 的数据流，圈出至少 5 条信任边界。
  • 解释 jailbreak、direct prompt injection 和 agent hijacking 的攻击者控制面有何不同。
  • 为什么 role=system 不是 access control？哪个组件应该做强制授权？
  • 对 send_email(recipient, body) 写出 subject/resource/action/arguments 级别的授权规则。
  • 跑 K04，解释未知参数为什么必须 fail closed。
  • 说出 memory 记录至少 6 个必要 metadata，并解释“读取时重新授权”。
  • 跑 K05，说明 wrong tenant、expired 和 untrusted source 分别拦什么。
  • 解释 MCP 中 token passthrough 和 confused deputy 的危险。
  • 手算一组 USR/ASR/UAR/FPR，说明为什么 ASR=0 仍可能是一个坏系统。
  • 跑 K07，沿一条间接注入 case 解释 observation → proposal → gateway → audit → metric 的完整证据链。
  • 跑 K08，解释为什么 manifest 指纹能发现变化，却不能证明首次安装的工具安全。
  • 运行 projects/secure-agent/run_demo.py，检查 audit 中正文被脱敏，并指出项目明确不覆盖的生产能力。
  • 为你的作品集项目写 5 个 benign cases 和 5 个 adversarial cases，每个都标注预期外部状态。

12 与主线的连接

  • ← F 的 tokenizer/role 让你理解模型为什么不能提供强制指令-数据隔离。
  • ← H 的 SQLi/XSS 输入边界思维在 Agent 中变成“模型输出也是不可信输入”。
  • ← K 的 prompt injection 是入口；本篇关心注入之后的 tool/memory/identity/authorization 如何决定实际损害。
  • → M 用自动化红队框架扩大场景，但评估单位仍然是“任务 + 攻击目标 + 实际状态”。
  • → O 可以从 AgentDojo 的防御缺口、memory provenance 或 per-tool authorization 评测做本科论文。
