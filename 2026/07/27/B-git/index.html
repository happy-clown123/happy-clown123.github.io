1. 基础概念

Git 是分布式版本控制：每个克隆都是完整仓库（含全部历史），不依赖中央服务器也能提交。

1.1 什么是版本控制

版本控制 = 记录文件随时间的变化，随时能回到某个历史版本。演进：本地（RCS）→ 集中式（SVN）→ 分布式（Git）。

1.2 核心思想：快照，不是差异

传统 VCS 存”初始文件 + 每次的差异”。Git 存的是每次提交时全部文件的快照——没变的文件只保留一个指向上次快照的链接，不重复存。

理解这点很重要：Git 的 commit 是一次”拍照”，不是”补丁”。所以回退、比对都极快。

1.3 三个区域（必懂）

  • 工作区（Working Directory）：你直接编辑的文件。
  • 暂存区（Staging / Index）：下次提交的文件清单（git add 把改动放这）。
  • 版本库（Repository / .git）：真正存提交历史的地方（git commit 落盘到这里）。

    一次提交的流程永远是：工作区改 → add 进暂存区 → commit 进版本库。

1.4 文件的四种状态

  • 未跟踪（Untracked）：Git 还没管它。
  • 已修改（Modified）：改了，但没进暂存区。
  • 已暂存（Staged）：改了，且已 add。
  • 已提交（Committed）：已 commit，安全存进版本库。

4. 撤销与回退

4.1 撤销工作区修改（git restore / checkout）

4.2 取消暂存（git reset HEAD / restore –staged）

4.3 修改最后一次提交（git commit –amend）

⚠️ --amend 会改写最后一次提交的历史（产生新哈希）。只对个人未推送的提交用；已 push 的别 amend，否则会和协作者冲突。

4.4 回退到历史提交（git reset –soft / –mixed / –hard）

⚠️ --hard 会永久删除未提交的改动。回退前先 git status 确认没有想留的东西。

4.5 安全撤销（git revert，不改写历史）

已 push 的提交要撤销，用 revert 而非 reset——它不改写公开历史，协作者 pull 不会炸。

5. 分支管理

5.1 分支是什么

分支 = 一个指向某次提交的可变指针。Git 建分支极快（只写一个 41 字节的文件），所以鼓励”一个功能一个分支”。

5.2 创建与切换（git branch / switch）

5.3 合并分支（git merge）

5.4 变基（git rebase）

⚠️ 黄金法则：只 rebase 你本地、还没 push 的分支。已公开的分支别 rebase，否则协作者历史错位。rebase vs merge 的选择见 §10.3。

5.5 分支冲突与解决

冲突发生在：两个分支改了同一文件的同一处，merge / rebase 无法自动合并。

💡 冲突不可怕——它就是 Git 在问你”这俩改法你要哪个”。解决后 add + commit / rebase --continue 即可。

9. 忽略文件（.gitignore）

有些文件不该进版本库：依赖目录（node_modules/ venv/）、构建产物、日志、密钥。用 .gitignore 告诉 Git 忽略它们。

9.1 忽略规则语法

  • 空行 / # 开头 = 注释，被忽略
  • * 匹配零个或多个任意字符；? 匹配一个；[abc] 匹配括号内任一个
  • 以 / 开头 = 只匹配当前目录（不递归子目录）
  • 以 / 结尾 = 匹配目录
  • ** 匹配任意中间目录（a/**/z 覆盖 a/z、a/b/z…）
  • ! 取反（白名单，但已被父规则忽略的无法再”取消忽略”）

9.3 敏感信息防护（密钥 / 凭证不入库）

🔑 密钥永远不进 git。误提交后要立刻：① 作废该密钥/换密码；② 从 git 历史彻底删（见 §12.2）。.env 用 export 注入（见 linux.md §11），脚本里 os.getenv() 读。

10. 协作工作流

10.1 Fork + Pull Request 流程

给别人仓库贡献的标准方式：

  1. 在平台点 Fork → 复制一份到你账号下
  2. git clone 你 Fork 的仓库，建分支改代码
  3. git push 到你 Fork → 在原仓库发 Pull Request（PR）
  4. 维护者 review 后合并

10.2 同步上游（upstream）

10.3 rebase 工作流（保持线性历史）

rebase 让历史像一条直线、好读；merge 保留真实分叉。团队约定优先——个人分支随意，共享分支听队规。

10.4 Code Review 要点

  • 一个 PR 一件事，别塞一堆不相关的改
  • 提交信息写清”为什么改”，不只”改了啥”
  • 大改动拆小提交，便于 review
  • 看别人 PR 时重点查：逻辑错误、安全漏洞（注入/越权）、密钥是否误入、测试是否覆盖

11. 子模块与其他

11.1 子模块（git submodule）

把另一个仓库作为当前仓库的子目录嵌入（固定某个提交）。

11.2 二分查找（git bisect）

用二分法快速定位”哪一次提交引入了 bug”。

11.3 钩子（git hooks）

仓库 .git/hooks/ 里的脚本，在特定事件（commit / push 前）自动跑。

💡 团队可用 hooks 强制规范（如禁止提交 .env、跑 pytest）。个人也能用 pre-commit 防误提交密钥。

12. 安全与最佳实践

12.1 提交签名（GPG / SSH 签名）

签名让他人验证”这提交确实是你发的”，防伪造。

12.2 敏感信息泄露后的处理

密钥误提交到 git 历史后，光 git rm 不够——历史里还在。必须改写历史：

🔑 第一原则：泄露后立即作废密钥/换密码，再清历史。清历史不能替代”密钥已暴露”的事实。

12.3 私有仓 vs 公开仓的边界

  • 私有仓：源码、未发表实验、论文草稿、任何含思路的东西
  • 公开仓：只放愿意公开的内容（如已发布的博客产物、开源项目）
  • 你自己的实践：源码笔记存私有学习仓；只有发布到博客的内容经部署工具进公开 Pages 仓

    边界清晰，才不会把”还没想清楚的东西”或”练手代码”误公开。

12.4 提交信息规范（Conventional Commits）

💡 好提交信息 = 三个月后你自己看得懂”那天到底干了啥”。AI+安全 实验多、迭代快，规范信息能救命。
